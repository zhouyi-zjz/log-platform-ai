# 高并发面试准备：基于 log-platform-ai 的场景构建与完整解决方案

> 适用：应聘资深 Java 后端 / 中间件方向，需要结合"真实项目"回答高并发问题的场景。
> 本文所有技术点均锚定本仓库（`log-platform-ai`）真实代码与配置，你可以对着代码逐条讲，比空谈概念更有说服力。

---

## 0. 先答"有没有高并发场景"——结论与判断口径

**有，而且很典型。** 判断一个系统是否存在高并发，不要只看 QPS 数字，要看**压力的形态**：

| 判断维度 | 本项目事实 | 结论 |
|---|---|---|
| 是否天然存在高吞吐写入 | 日志采集链路，所有接入项目持续灌日志 | **是，写放大是主场景** |
| 是否有突发洪峰 | 大促、线上故障、安全攻击时日志量瞬时暴涨（远超日均） | **是** |
| 是否有重读放大 | 监控大屏、故障排查时多人并发查询/聚合 ES | **是** |
| 是否有瞬时热点 | 某大项目/故障服务日志集中，数据倾斜 | **是** |
| 是否有异步/AI 慢接口 | AI 日志分析（SSE 流式），模型调用慢而贵 | **是** |

**一句话定位**：本项目是一个"**写多读少、写入不可丢、读取要快**"的日志平台。写侧是吞吐型高并发（追求每秒条数与稳定性），读侧是突发型高并发（追求延迟与隔离）。容量模型文档（`docs/capacity/log-platform-capacity-model.md`）给出的设计基准：日均 500 万条、平均 57.9 EPS、设计峰值 300 EPS——这个规模在面试里可以直接说"当前是中小规模，但我按生产化容量模型设计了 Kafka 分区、消费并发、ES bulk 与查询限流，可平滑扩展到数千 EPS"。

面试开场答法（建议背下来）：

> "我们这个项目是日志采集分析平台。它最典型的高并发场景在**写入链路**：所有业务系统把日志源源不断地灌进来，平时几十条/秒，故障或大促时能瞬间涨到几百上千条/秒，且日志**不允许丢**。所以我把写侧设计成了『Fluent Bit 本地缓冲 → Kafka 削峰填谷 → 批量消费 → ES Bulk 写入』的异步管道；读侧则用限流、缓存、深分页优化和读写隔离来扛突发查询。下面我按场景讲具体的解决方案。"

## 1. 架构总览（先讲清楚全链路，再讲压力点）

```
业务应用（OTel/SkyWalking Agent 采集 Trace + 应用日志 JSON）
        │
        ▼
Fluent Bit（文件/容器 stdout，本地磁盘缓冲，可 Kafka output 或 HTTP）
        │
   ┌────┴───────────────┬──────────────────────┐
   ▼                     ▼                       ▼
POST /monitor/api/logs/ingest（HTTP 入口，返回 202）    直连 Kafka
        │
        ▼
Kafka logs.raw（6 分区 / RF2，key=project|service|env）
        │
        ▼
Spring 消费端（批量拉取 → 字段归一化 normalizer）
        │
        ▼
Elasticsearch 8.x Data Stream（ES Bulk NDJSON，ILM 7 天）
        │
        ▼
查询链路：/search  /{id}  /{id}/context  /aggregations
        │（LogQueryLimiter 限流 → LogQueryService 拼 DSL → ES）
        ▼
前端 Vue /monitor（监控大屏、检索、AI 分析入口）
```

**高并发压力点在两个位置（对应两类经典场景）**：

- **写侧压力点**：`ingest 入口 → Kafka → 消费端 → ES bulk`，瓶颈在 ES 写入吞吐与消费 lag。
- **读侧压力点**：`查询接口 → ES _search/_aggregations`，瓶颈在 ES 查询线程池、深分页与聚合开销。

## 2. 场景一（核心）：日志采集写入洪峰——写放大场景

### 2.1 场景描述

这是日志平台**最典型**的高并发场景。平时 60 EPS，双十一/故障演练/被攻击时 5 分钟暴涨到 2000+ EPS。要求：**日志一条不能丢、延迟可容忍秒级、不能把后端 ES 打崩**。这里"高并发"的难点不在 QPS 有多高，而在**吞吐瞬时冲高 + 强一致（不可丢）+ 下游慢**三者叠加。

### 2.2 为什么难（面试要讲出这个矛盾）

1. **削峰 vs 实时性**：直接同步写 ES，入口 QPS 一高 ES 就拒绝，日志丢；但又要尽量实时。
2. **吞吐 vs 顺序**：要吞吐就得并行，并行会破坏"同一业务日志按序"。
3. **慢下游的背压**：ES bulk 一抖动，消费端要么堆积要么丢数据，怎么传导压力才不丢。
4. **重复消费**：Kafka 可能重复投递，ES 写入必须幂等。

### 2.3 完整解决方案（对应本项目真实代码）

**① 分阶段 + 削峰填谷：Kafka 作为缓冲队列（项目核心设计）**

采集不直接进 ES，先进 Kafka。Kafka 是高性能、可持久化的 MQ，天然把"瞬时洪峰"摊平成"消费端按自己的节奏拉取"，这就是**削峰填谷**。
对应代码：`LogIngestService.publish()` 用 `kafkaTemplate.send()` 异步投递，`LogIngestController` 只校验 Token、大小就返回 `202 Accepted`，**不在 Web 线程同步写 ES**。面试话术："HTTP 入口只负责提交 Kafka 就返回，把最贵的 ES 写入从请求线程挪到后台消费线程，Web 线程池不会被慢下游拖垮。"

**② 批量写：减少与 ES 的交互次数**

消费端用 `@KafkaListener(batchListener=true)` 批量拉取，攒批后 `ElasticsearchLogWriter.writeBulk()` 一次 `_bulk` 写入（`bulkMaxActions=1000`、`flushIntervalMs=1000`）。批量能把"每事件一次请求"降成"每 1000 事件一次请求"，吞吐量级提升。
面试话术："ES 是典型的大批量友好存储，我用批量监听 + Bulk API，按 1000 条或 1 秒先到先 flush，吞吐从几十提升到几千条/秒。"

**③ 并行度由 Kafka 分区决定：分区设计（项目容量模型已算）**

一个分区的消费是顺序的，吞吐有限；**消费并行上限 = 分区数**。容量模型建议 `partitions >= ceil(EPS_peak / 500)`，本项目起步 6 分区、预留 12。消费者实例数 ≤ 分区数，否则有实例空转。
面试话术："我把日志 Topic 设计成 6 分区、副本 2，分区数既决定了 Kafka 存储并行度，也决定了消费端能开多少并发，扩容瓶颈不在机器而在分区数。"

**④ key 设计：吞吐与顺序的平衡**

`LogIngestService` 用 `project.id|service.name|environment` 做 Kafka key，**同一业务日志进同一分区、保持顺序**，同时避免单个大项目独占全部分区（key 粒度到 service 就分散了）。面试要能说出权衡：key 太粗→热点分区；key 太细（每条随机）→顺序全丢。本项目选择"到 service 级"，顺序保留到服务级，够用且不热点。

**⑤ 可靠性兜底：重试 + 死信，绝不静默丢**

`LogIngestConfiguration` 里 `DefaultErrorHandler + DeadLetterPublishingRecoverer`：ES bulk 失败 → `FixedBackOff(1000, 2)` 重试 3 次 → 仍失败投递到 `logs.raw.DLT` 死信。`writeBulk` 检测到 `errors=true` 会抛异常触发重试，而不是吞掉单条。
面试话术："写 ES 是整批提交，一批里任何一条失败就整批重试，重试有上限，超过进死信队列，保证不阻塞分区、不静默丢日志。死信可人工/自动复盘。"

**⑥ 幂等：ES 用 create 操作防重复**

`ElasticsearchLogWriter` 统一用 `{"create":{}}`（Data Stream 要求）。create 遇到已存在的 _id 会报冲突，Kafka 重复消费时就能被识别而不是覆盖污染数据。这是**消费幂等**的落地。

**⑦ 入口防护：限流 + 大小校验，防恶意刷量**

`LogIngestController` 校验 payload ≤ 1MB（`maxPayloadBytes`），Token 鉴权（`isValidToken` 用 `MessageDigest.isEqual` 防时序攻击）。生产再加采集端 IP 限流、按项目配额。

**⑧ 可观测与扩容阈值（容量模型第 4 节）**

监控 Kafka consumer **lag**、ES **bulk 拒绝率**、bulk P95。扩容信号：
- lag 连续 5 分钟 > 30s → 先加消费实例/分区，再看 ES bulk 拒绝率；
- ES 写拒绝率 > 1% 或 bulk P95 > 2s → 降批量、加 data 节点、扩写线程池，**禁止盲目加分片**。

### 2.4 面试官可能追问（提前备好）

- **为什么用 Kafka 而不是直接写 ES？** 削峰填谷、解耦、背压缓冲、可重放（2 天保留窗口）；直接写 ES 会把入口 QPS 和 ES 写入强耦合，一抖动就互相拖累。
- **Kafka 为什么能高吞吐？** 顺序写磁盘 + page cache + 零拷贝 + 批量 + 分区并行 + 副本 ISR 机制。面试提"顺序追加 + OS 页缓存 + sendfile 零拷贝"即可。
- **重复消费怎么办？** 消费端幂等（ES create 幂等）+ 唯一键；重试交给 offset 语义，只有"处理成功且提交 offset"才算消费成功。
- **顺序性怎么在并发下保住？** 同 key 同分区顺序；需要更强顺序就收窄 key 粒度或局部串行。
- **分区扩容会影响顺序吗？** 会，key 重新哈希；所以扩容要评估，热点用"新增 topic/重分区"而非粗暴加分区。

## 3. 场景二：查询接口并发风暴——读放大场景

### 3.1 场景描述

故障发生时，几十上百个研发同时打开监控大屏刷日志、跑聚合、导数据。ES 查询是重操作（倒排扫描 + 聚合 + 取文档），**并发查询会互相抢 ES 查询线程池**，一个慢查询能把整库查询拖垮。

### 3.2 完整解决方案

**① 分级限流 + 全局并发闸门（项目已有，需讲清设计）**

`LogQueryLimiter` 两层保护：
- **单用户/IP 速率**：`ConcurrentHashMap` 按 `user@ip` 做**滑动窗口（分钟级计数）**限流，`rateLimitPerMinute=120`。
- **全局并发**：`Semaphore(maxConcurrent=20)`，超了直接 429，防止 Web 并发把 ES 打满。
面试要主动指出**当前实现是单实例内存限流**，多实例部署必须换 Redis 分布式限流（令牌桶/滑动窗口），这是体现"知道演进方向"的加分点。

**② 查询超时 + 线程池隔离**

ES 查询 `timeout=3s`、HTTP read timeout 5s；用独立 RestClient/线程池隔离"搜索 vs 聚合 vs 导出"，避免一个重聚合占满所有线程。聚合接口额外限 `groupBy ≤ 3`、字段白名单、`terms size ≤ 100`，防高开销查询绕过限制。

**③ 深分页优化：search_after 替代 from+size（项目已落地）**

`LogQueryService` 固定用 `search_after`（`@timestamp + _id` 双字段游标）翻页，且**禁止前端传自定义游标**（校验恰好两个值）。同时 `track_total_hits=10000` 截断精确计数。
面试话术："from+size 每翻一页都要把前 N 条全算一遍，越深越贵，还会被 ES 默认 max_result_window 限制；我用 search_after 游标 + 排序键定位，深翻页代价恒定。"

**④ 缓存：多级缓存挡读放大**

- 前端：分页、防抖、滚动加载，避免反复全量查询；
- 应用层：热查询结果缓存到 Redis（短 TTL），同参数命中直接返回；
- ES 层：`query cache` 对热 filter 生效；监控大屏的固定聚合结果**预计算成独立指标索引**，大屏读预聚合索引而非实时扫全量。
面试话术："监控大屏是最典型的读放大——几百人看同一批指标。把固定维度聚合预聚合成独立索引，大屏只查聚合结果，实时扫全量的成本降到零。"

**⑤ 读写隔离 + 冷热分层**

- 写走 ES 主分片，读尽量走副本/独立查询节点；
- ILM 把最近热数据（当天/7 天）放高性能盘，历史下冷阶段；普通用户只能查当天（`LogQueryWindowService` 强制权限窗口），天然限定查询范围。

**⑥ 降级熔断**

ES 超时/不可用 → 返回 503/504 明确提示"缩小时间范围或稍后重试"（`LogQueryController` 已做）；聚合接口可降级为缓存结果或简化查询。面试说"查询侧兜底是降级而不是无限重试"。

### 3.3 面试官可能追问

- **Redis 分布式限流怎么做？** 令牌桶（Lua 脚本保证原子）：`KEYS[1]` 存令牌余量与上次时间；或滑动窗口（zset 记录时间戳）。要提"用 Lua 保证 get-and-set 原子性，避免竞态"。
- **限流放哪一层？** 网关（全局、全局配额）→ 应用（业务级、按用户/项目）→ ES（保护下游）。分层职责不同。
- **缓存一致性怎么保证？** 日志只增不改（append-only），缓存几乎不会脏，给短 TTL + 幂等写即可；面试里提"日志场景是只写不改，天然适合缓存，不一致窗口极小"。
- **为什么 ES 慢查询会拖垮整个集群？** ES 查询线程池是共享的，慢查询占住线程 + 产生 GC 压力；所以必须限时、限并、限聚合规模。

## 4. 场景三：热点日志 / 数据倾斜

### 4.1 场景描述

一个核心服务的日志占全平台 80%，因为 key 固定到该 service，导致**单 Kafka 分区热点**：该分区消费是顺序的，成了吞吐瓶颈，其他分区空转；同时 ES 单分片过大、查询慢。

### 4.2 完整解决方案

1. **分区策略**：对热点 key 增加**随机/批次后缀**打散（牺牲该业务严格顺序），或给大项目独立 Topic + 更多分区。
2. **局部聚合**：热点项目在消费端先按 5 分钟窗口本地聚合（count/sum/错误码），只把聚合结果写 ES，量骤降。
3. **ES 分片均衡**：避免单 backing index 大分片（容量模型：单分片 10~30 GiB）；数据量小优先少分片，不盲目加分片。
4. **采样降噪**：Trace 侧 OTel 按比例采样，日志侧对低价值 debug 日志采样，削掉大头。
面试话术："数据倾斜的本质是『key 粒度 × 分区数』没匹配好。要么打散 key 换吞吐，要么给大对象单独资源池，要么先聚合再落地——按业务对顺序的敏感度选。"

### 4.3 追问

- **顺序性和扩展性冲突怎么取舍？** 答：按业务定。需要严格顺序的业务收窄 key；能容忍轻微乱序的用随机分区换吞吐；中间态用"局部聚合 + 分区重排"。
- **Kafka 分区扩容为什么不能随意？** 分区数增加会触发重平衡、重排 offset；且 key 路由到新分区的数据顺序变化。生产上分区数应一次规划到位或预留。

## 5. 场景四（基础但常考）：登录 / 鉴权被刷

### 5.1 场景

登录接口无状态 Token，被暴力破解/脚本刷验证码；Token 校验在网关高并发下成为热点。Spring Security + 数据库用户（`DatabaseUserDetailsService`）。

### 5.2 方案

- **JWT 无状态化**（pom 已引入 jwt）：登录签发 Token，校验不查库，网关/过滤器直接验签，天然扛并发。
- **防爆破**：登录失败计数（Redis，IP+用户名 key），超过阈值锁定 + 验证码/滑块；`LoginController` 已返回明确错误。
- **Token 生命周期**：短有效期 + refresh token；踢人下线用 Token 黑名单/版本号（无状态与可撤销的权衡）。
- **密码安全**：BCrypt 加盐（非明文）、登录限流。
面试话术："鉴权要无状态才能扛并发，但无状态牺牲了可撤销性，我用『短 Token + refresh + 黑名单』两全。"

## 6. 场景五（本项目类型延伸，AI 分析并发）

### 6.1 场景

日志平台的 AI 分析（摘要、异常根因、语义检索，前端走 SSE 流式，pom 已引入 okhttp-sse）。LLM 调用**慢（秒级）且贵（按 token）**，高并发会把模型网关打爆、成本爆炸。

### 6.2 方案

- **异步化 + 队列**：AI 请求不占 Web 线程，提交任务队列异步执行；前端 SSE 接收流式结果（okhttp-sse 已具备）。
- **结果缓存 + 请求合并**：相同/相近查询合并为一次模型调用，热点问题只调一次；已生成结果缓存复用。
- **限流与配额**：按用户/项目限每分钟 AI 请求数、按 token 额度控制，防止刷爆。
- **超时 + 降级**：模型超时/不可用 → 返回模板化分析/规则匹配结果，而不是无限等待；LLM 失败不阻塞主查询。
- **语义检索**：向量库（embedding）读写独立资源池，与倒排检索隔离。
面试话术："AI 接口的并发瓶颈不在吞吐在『慢+贵』。我用队列削峰、缓存合并请求、按 token 配额、流式返回，把 LLM 当最稀缺的资源来保护。"

## 7. 高频追问速答（资深开发必问，先背下来）

| 问题 | 一句话参考答案 |
|---|---|
| 什么是高并发？ | 单位时间大量请求/吞吐，难点在稳定性（不被打垮）而非单纯的数字大 |
| 高并发三板斧？ | 缓存（读）、异步/队列（削峰解耦）、限流/降级/熔断（保护） |
| 限流常见算法？ | 固定窗口（简单有临界突刺）、滑动窗口（平滑）、令牌桶（允许突发）、漏桶（恒定速率） |
| 熔断与降级区别？ | 熔断是"下游挂了切断调用"（如 sentinel/Resilience4j），降级是"能力不足给次优结果" |
| 缓存三大问题？ | 穿透（查不存在→布隆过滤）、击穿（热点失效→互斥重建）、雪崩（集体失效→TTL 打散+多级） |
| Kafka 怎么保吞吐？ | 顺序写 + 页缓存 + 零拷贝 + 批量 + 分区并行 + 副本 ISR |
| 为什么 ES 适合日志？ | 倒排全文 + 聚合 + 时序 Data Stream + 水平分片，天然匹配"写入海量、检索快" |
| ES 深分页？ | 用 search_after，避免 from+size 的开销爆炸 |
| 幂等怎么实现？ | 唯一键 + 业务幂等（本项目 ES create）+ 消费端去重 |
| 读写分离意义？ | 写主读从，隔离 IO，防止读放大拖垮写入吞吐 |

## 8. 结合本项目的落地改造点清单（体现"我懂演进"）

面试时主动说"当前是第一版，我会这样演进"，非常加分：

1. `LogQueryLimiter` 从内存限流 → **Redis 分布式限流**（多实例配额一致）。
2. 入口加**网关层限流**（全局 + 按项目），采集 Token 改每项目独立。
3. 查询结果**多级缓存** + 大屏**预聚合索引**。
4. 写侧加**背压监控与自动扩缩**：lag、bulk 拒绝率上告警，Kafka 分区预留扩容。
5. ES 查询**读写分离**（副本节点）与**线程池隔离**（搜索/聚合/导出）。
6. 冷热分层 + **快照/归档**，长周期留存走对象存储，控制热存储规模。
7. AI 分析补 **SSE 流式 + 队列 + token 配额**（当前 UI 已有 SSE 基础）。
